공유기에서 포트포워딩 규칙까지 만들었는데 외부에서 접속되지 않는 경우가 있습니다. 이때 포트 번호를 계속 바꾸거나 같은 규칙을 다시 만드는 것보다 먼저 확인해야 할 것이 있습니다. 포트를 받을 프로그램이 실제로 실행 중인지, 규칙이 현재 PC를 가리키는지, 그리고 외부 연결이 공유기까지 도착할 수 있는 환경인지입니다.

포트포워딩은 닫힌 포트를 강제로 여는 기능이라기보다 공유기에 도착한 연결을 내부의 특정 기기로 전달하는 규칙입니다. 따라서 연결 경로 중 한 곳만 막혀도 테스트에서는 포트가 닫힌 것으로 보입니다.

## 1. 프로그램이 해당 포트를 실제로 사용 중인지 확인

가장 먼저 서버나 프로그램을 실행한 상태에서 테스트합니다.

예를 들어 게임 서버에 TCP 25565를 전달하도록 설정했더라도 서버 프로그램이 실행되지 않았다면 외부 포트 검사에서 닫힌 것으로 표시될 수 있습니다. 공유기는 연결을 PC까지 전달했지만 그 연결을 받아줄 프로그램이 없는 상태이기 때문입니다.

Windows에서는 명령 프롬프트나 PowerShell에서 다음 명령으로 현재 대기 중인 포트를 확인할 수 있습니다.

```
netstat -ano | findstr :25565
```

25565 부분은 확인하려는 포트 번호로 바꿉니다.

LISTENING 상태가 보인다면 해당 포트를 기다리는 프로세스가 있다는 뜻입니다. 아무것도 나오지 않는다면 공유기 설정보다 프로그램의 포트 설정부터 다시 확인합니다.

## 2. 같은 PC 안에서 먼저 접속해봅니다

외부 접속을 테스트하기 전에 서버가 실행되는 PC 자체에서 서비스가 정상인지 확인하는 것이 좋습니다.

웹 서비스라면 localhost와 해당 포트로 접속하고, 게임 서버라면 프로그램이 제공하는 로컬 접속 방법을 사용합니다. 같은 PC에서도 접속되지 않는다면 포트포워딩이 원인은 아닙니다.

그다음 같은 공유기에 연결된 다른 PC나 기기에서 서버 PC의 내부 IP로 접속해봅니다.

```
서버 PC: 192.168.0.50
포트: 25565
```

이 경우 같은 네트워크에서는 192.168.0.50과 해당 포트를 이용해 테스트할 수 있습니다.

로컬 네트워크에서는 되는데 외부에서만 안 된다면 그때부터 공유기와 인터넷 회선 쪽으로 범위를 좁힐 수 있습니다.

## 3. 포트포워딩 대상 IP가 현재 PC와 같은지 확인

포트포워딩 규칙에는 보통 내부 IP 또는 대상 IP를 입력합니다.

문제는 PC가 공유기에서 자동으로 IP를 받는 경우 주소가 나중에 바뀔 수 있다는 점입니다. 어제 192.168.0.50이었던 PC가 재부팅 후 192.168.0.73을 받았다면 기존 규칙은 더 이상 그 PC를 가리키지 않습니다.

Windows에서 ipconfig를 실행해 현재 IPv4 주소를 확인한 뒤 공유기에 입력된 대상 IP와 비교합니다.

주소가 자주 바뀌는 것을 막으려면 공유기의 DHCP 예약 기능을 이용해 해당 PC에 같은 내부 IP가 계속 할당되도록 설정하는 방법이 편합니다.

## 4. TCP와 UDP를 구분합니다

포트 번호가 맞더라도 프로토콜이 다르면 연결되지 않을 수 있습니다.

프로그램이 TCP를 사용하는데 공유기에서 UDP만 전달했거나 그 반대인 경우입니다. 게임에 따라 TCP와 UDP를 모두 사용하면서 각각 다른 포트를 요구하기도 합니다.

필요한 포트와 프로토콜은 임의의 블로그 목록보다 사용하는 프로그램이나 게임 서버의 공식 문서를 먼저 확인하는 편이 안전합니다.

공유기에 TCP/UDP 또는 BOTH 같은 옵션이 있더라도 프로그램이 실제로 어떤 프로토콜을 사용하는지는 별도로 확인해야 합니다.

## 5. Windows 방화벽에서 막히는지 확인

공유기가 연결을 제대로 전달해도 Windows 방화벽에서 해당 연결을 차단할 수 있습니다.

Windows 보안의 방화벽 설정에서 프로그램이 허용되어 있는지 확인합니다. 직접 인바운드 규칙을 만들었다면 포트 번호, TCP/UDP, 적용되는 네트워크 프로필도 함께 봅니다.

문제 확인을 위해 방화벽 전체를 장시간 꺼두는 것보다는 필요한 프로그램이나 포트에 대한 규칙을 확인하는 편이 낫습니다.

백신이나 보안 프로그램이 자체 방화벽 기능을 제공한다면 Windows 방화벽 외에 해당 프로그램의 설정도 확인해야 할 수 있습니다.

## 6. 집 안 와이파이에서 공인 IP로 테스트하면 실패할 수도 있습니다

포트포워딩을 제대로 설정했는데 집 안에서 자신의 공인 IP로 접속했을 때만 실패하는 경우가 있습니다.

일부 공유기는 NAT Loopback 또는 Hairpin NAT를 지원하지 않습니다. 이런 장비에서는 같은 내부 네트워크에 있는 기기가 공인 IP를 이용해 다시 내부 서버로 들어오는 연결이 제대로 동작하지 않을 수 있습니다.

그래서 외부 접속 여부를 확인할 때는 스마트폰의 와이파이를 끄고 모바일 데이터로 접속하거나 실제 외부 네트워크에서 테스트하는 것이 정확합니다.

내부에서는 내부 IP로 정상 접속되고 모바일 데이터에서는 공인 IP로 정상 접속된다면 포트포워딩 자체는 작동하고 있는 것입니다.

## 7. 공유기의 WAN IP와 공인 IP를 비교합니다

여기까지 정상인데 외부에서 여전히 접속되지 않는다면 공유기 관리 페이지에서 WAN 또는 인터넷 IP를 확인합니다.

그리고 인터넷에서 확인되는 공인 IP와 비교합니다.

두 주소가 다르다면 공유기 앞에 또 다른 라우터가 있는 이중 NAT 환경이거나 인터넷 제공업체가 CGNAT를 사용하는 환경일 수 있습니다.

이중 NAT라면 바깥쪽 공유기에서도 연결 경로를 처리하거나 NAT를 한 단계로 줄여야 합니다. CGNAT라면 사용자가 자신의 공유기에서 포트를 전달해도 외부 연결이 통신사 NAT를 통과하지 못할 수 있습니다.

이 경우 포트포워딩 규칙을 계속 수정해도 해결되지 않습니다. 인터넷 제공업체에 공인 IPv4 사용 가능 여부를 확인하는 편이 빠릅니다.

## 포트 검사 사이트에서 닫힘으로 나오면 어디까지 확인해야 할까

다음 순서로 보면 원인을 비교적 빨리 좁힐 수 있습니다.

프로그램 실행 → 포트 LISTENING 확인 → 같은 PC에서 접속 → 같은 LAN의 다른 기기에서 접속 → 대상 내부 IP 확인 → TCP/UDP 확인 → Windows 방화벽 확인 → 실제 외부망에서 테스트 → WAN IP와 공인 IP 비교

앞 단계에서 실패했다면 뒤쪽 공유기 설정부터 만질 필요가 없습니다.

예를 들어 같은 LAN에서도 서버에 접속되지 않는다면 CGNAT를 조사할 단계가 아닙니다. 반대로 LAN에서는 정상이고 방화벽과 포트 규칙도 맞는데 외부에서만 실패한다면 WAN 쪽을 확인할 차례입니다.

포트포워딩 문제는 설정 화면의 숫자 하나가 틀려서 생기기도 하지만, 실제로는 서버 프로그램, 내부 IP, 방화벽, 이중 NAT, CGNAT처럼 서로 다른 지점에서 같은 ‘접속 안 됨’ 증상이 나타납니다. 연결 경로를 안쪽에서 바깥쪽으로 하나씩 확인하면 공유기 설정을 무작정 반복하는 것보다 원인을 찾기 쉽습니다.
